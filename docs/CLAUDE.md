# 문서(docs) 작성 원칙

이 폴더의 문서를 추가/수정하는 모든 에이전트는 아래 원칙을 따른다.

## 기능 문서 시스템 (Feature Docs)

기능 문서는 **개발자가 아닌 사용자를 독자로 상정한 기능 설명서**다. 코드 주석이나 설계 문서와 구분된다.

### 1. 위치와 폴더 구조

- 모든 기능 문서는 [`docs/features/`](./features/) 폴더 하위에 **기능별 '폴더'** 로 관리한다. (이하 **개별 기능 문서 폴더**)
- 개별 기능 문서 폴더 이름은 다음 규칙을 따른다:
  - **3자리 숫자 인덱스**를 접두사로 붙인다. (`001`, `002`, …)
  - **영문**으로 작성한다.
  - 인덱스와 기능명은 **하이픈**(`-`)으로 잇는다.
  - 기능명 내부의 공백은 **언더스코어**(`_`)로 잇는다.
  - 예: `001-editor_context_tag`
- 개별 기능 문서 폴더에는 해당 기능 문서의 **언어별 번역본들**을 저장한다. (예: `en.md`, `ko.md`, …)

### 2. 메타 파일 (색인)

- 개별 기능 문서 폴더들을 모아둔 [`docs/features/`](./features/) 아래에는 [`docs/features/CLAUDE.md`](./features/CLAUDE.md)(이하 **메타 파일**)가 있고, 개별 기능 문서 폴더들을 **색인**하는 역할을 포괄한다.
- 메타 파일에 기능을 색인할 때는 **기능별로 불릿포인트 마크다운 링크 한 줄**이면 충분하다.

### 3. 작성 톤과 내용

- 사용자를 독자로 상정하므로, **업데이트 노트와 유사한 톤앤매너**로 작성한다.
- 사용자에게 안내되어야 하는 내용을 **최대한 상세하면서도 쉽게** 작성한다.
- 관련된 **버전·PR·이슈** 등을 적극적으로 링크하여 맥락을 충분히 제공한다.

### 4. 작성 책임

- 모든 기능 PR은 가능한 경우라면 **반드시 기능 문서를 작성하거나 최신화**하기 위해 노력해야 한다.
- 사용자가 기능 문서 작성을 지시하지 않더라도, **기능 문서 작성을 적극적으로 제안**하여, 사용자가 명시적으로 거절하지 않는 한 작업을 놓치지 않도록 돕는다.

## 트러블슈팅 문서 시스템 (Troubleshooting Docs)

트러블슈팅 문서는 **자주 발생하는 문제 중, 아직 우리가 직접 고치지 못했지만 알려진 해결 방법이 있는 것**을 다룬다. 기능 문서와 독자는 같지만 목적이 다르다 — 기능 문서가 "무엇을 할 수 있는가"라면, 트러블슈팅 문서는 "왜 안 되는가와 어떻게 우회하는가"다.

**원인이 우리 밖에 있더라도 그것을 문서의 화법으로 삼지 않는다.** 사실 관계로는 플랫폼·OS 제약이 맞더라도, "사용자 환경 때문"이라고 앞세우면 책임을 넘기는 것으로 읽힌다. 사용자가 겪는 것은 어디까지나 우리 제품이 안 되는 상황이다. 그래서 도입부는 **"아직 못 고쳤고, 대신 알려진 방법은 이것"**으로 쓴다. 기술적 원인은 각 문서의 `원인` 절에서 정확히 설명하면 충분하다.

### 1. 무엇을 트러블슈팅 문서로 만드는가

판별 기준은 **"우리 코드를 고쳐서 해결할 수 있는가"** 하나다.

| 성격 | 처리 |
|------|------|
| 우리 코드의 버그 | 트러블슈팅 문서가 아니다. **고치고 릴리즈한다** |
| 플랫폼·런타임·OS·데스크탑 환경의 제약 | 트러블슈팅 문서로 만든다 |
| 사용자가 IDE 설정을 직접 손봐야 우회되는 것 | 트러블슈팅 문서로 만든다 |

이미 고쳐서 배포한 버그를 트러블슈팅에 남기지 않는다. 사용자가 불필요한 우회를 하게 된다.

### 2. 위치와 폴더 구조

기능 문서와 달리 **언어별 폴더로 나눈다.** 색인 파일(`README.md`)이 언어마다 필요하기 때문이다.

- 모든 트러블슈팅 문서는 [`docs/troubleshooting/`](./troubleshooting/) 하위의 **언어 폴더**에 둔다. (`en/`, `ko/`, `ja/`, `zh/`, `de/`, `es/`, `fr/`)
- 개별 문서 파일명은 다음 규칙을 따른다:
  - **번호를 붙이지 않는다.** 트러블슈팅 항목은 순서에 의미가 없고, 해결되면 사라질 수 있다.
  - **영문 슬러그**로 작성하고, 단어는 **하이픈**(`-`)으로 잇는다.
  - 같은 항목은 모든 언어 폴더에서 **동일한 파일명**을 쓴다. 상호 링크가 경로만 바꿔 성립해야 하기 때문이다.
  - 예: `wayland-clipboard.md`, `android-studio-jcef.md`

### 3. 색인 파일

- 각 언어 폴더에 `README.md`(색인)를 둔다. 이것은 에이전트용 메타 파일이 아니라 **사용자가 README에서 클릭해 들어오는 페이지**다.
- 항목은 **표**로 나열하고, 각 행에 문서 링크와 "이런 경우에 보세요"를 함께 적는다. 사용자가 자기 증상으로 찾을 수 있어야 한다.
- 색인 말미에 **"여기에 없는 문제라면"** 절을 두어 이슈 등록 경로와, 제보 시 함께 적어야 할 환경 정보를 안내한다.

### 4. 필수 구성 — 언어 전환 줄

**색인뿐 아니라 개별 문서에도 언어 전환 줄을 반드시 넣는다. 예외 없다.**

색인에만 넣으면 안 되는 이유는, 사용자가 **개별 문서 링크를 직접 받아 들어오는 경우가 많기 때문**이다. 이슈 답변이나 README에서 항목 링크를 바로 클릭해 들어온 사람은 색인을 거치지 않으므로, 문서 안에 전환 줄이 없으면 자기 언어로 갈 방법이 없다.

- 위치는 **문서 제목(`# …`) 바로 다음 줄**이며, 앞뒤로 빈 줄을 둔다.
- 형식은 루트 `README.md`의 언어 전환 줄을 그대로 따른다. `🌐` 로 시작하고, 항목은 ` | ` 로 잇는다.
- 언어 순서는 **`en ko ja zh es de fr`** 로 고정한다. 색인·개별 문서·루트 README가 모두 같은 순서여야 한다.
- **현재 언어는 볼드**(`**한국어**`)로 두고 링크를 걸지 않는다. 나머지는 전부 링크한다.
- 개별 문서의 링크는 **같은 항목의 다른 언어판**을 가리킨다(`../<lang>/<같은-파일명>`). 색인으로 보내면 안 된다 — 읽던 문서를 잃는다.
- 이것이 모든 언어 폴더에서 **파일명을 동일하게 유지해야 하는 이유**다. 파일명이 다르면 이 링크가 성립하지 않는다.

### 5. 필수 구성 — 관련 링크 챕터

**모든 트러블슈팅 문서는 마지막에 `관련 링크` 챕터를 반드시 포함한다. 예외 없다.**

이 챕터가 강제인 이유는, 트러블슈팅 문서가 다루는 문제는 대개 **우리가 고칠 수 없어서 오래 열려 있고**, 그동안 근거가 여러 곳에 흩어지기 때문이다. 근거를 문서 안에 모아두지 않으면, 다음에 이 문제를 다시 볼 때 조사를 처음부터 되풀이하게 된다.

아래 갈래 중 **해당하는 것을 모두** 넣는다. 없는 갈래는 생략한다.

| 갈래 | 무엇을 | 설명 |
|------|--------|------|
| 이 저장소의 이슈 | 메인 이슈, 중복으로 병합된 이슈, 아직 열려 있는 관련 이슈 | **붙이지 않는다** |
| 이 저장소의 PR | 이 문제를 부분적으로라도 다룬 변경 | **붙이지 않는다** |
| 벤더 티켓 | JetBrains YouTrack 등 | 붙인다. **열림/닫힘 상태와 닫힌 사유를 함께 적는다** |
| 다른 프로젝트의 같은 증상 | 같은 문제를 겪는 다른 플러그인의 이슈 | 붙인다 |
| 외부 참고 | OS·데스크탑 환경의 버그 트래커, 벤더 문서 | 붙인다 |

**이 저장소의 이슈·PR에는 대시 뒤 설명을 붙이지 않는다.** 링크 라벨에 이미 `#번호 — 제목`이 들어가므로, 뒤에 설명을 또 다는 것은 같은 내용을 두 번 적는 것이 된다.

**이 저장소의 이슈·PR은 번호 내림차순(최신순)으로 나열한다.** 중요도 순으로 손수 배열하면 항목이 늘어날 때마다 어디 끼워 넣을지 매번 판단해야 하고, 언어별로 순서가 갈라진다. 번호순은 기계적으로 결정되므로 7개 언어가 항상 같은 순서를 유지한다.

반면 **나머지 갈래에는 한 줄 설명을 붙인다.** 벤더 티켓은 라벨이 `JBR-10222` 같은 식별자뿐이라 설명이 없으면 무엇인지 알 수 없기 때문이다. 특히 **아직 열려 있는 티켓은 그 사실을 명시**한다 — 사용자가 투표해 우선순위를 올릴 수 있는 곳이기 때문이다.

### 6. 필수 구성 — 최종 업데이트 날짜

**색인을 포함한 모든 트러블슈팅 문서는 최종 업데이트 날짜를 적는다. 예외 없다.**

트러블슈팅 문서는 **오래 살아남는 대신 낡기 쉽다.** 우회책은 벤더가 문제를 고치는 순간 불필요해지고, 티켓의 열림/닫힘 상태도 바뀐다. 사용자가 이 문서를 믿고 IDE 설정을 바꾸기 전에, **이 정보가 언제 확인된 것인지** 알 수 있어야 한다.

**위치는 언어 전환 줄 바로 아래**, 즉 본문이 시작되기 전이다. 문서 끝에 두면 우회책을 다 읽고 IDE 설정까지 바꾼 뒤에야 날짜를 보게 된다. 신선도는 **읽기 전에 판단할 정보**이므로 위에 있어야 한다.

```
문서 제목 (h1)

언어 전환 줄 (🌐 …)

_최종 업데이트: 2026-08-22_

본문 첫 섹션 (h2)
```

- 언어별 표기: `Last updated` / `최종 업데이트` / `最終更新` / `最后更新` / `Última actualización` / `Zuletzt aktualisiert` / `Dernière mise à jour`
- 날짜는 `YYYY-MM-DD` 로 통일한다.
- **문서 내용을 고칠 때마다 날짜를 갱신한다.** 갱신하지 않으면 낡은 날짜가 남아, 날짜가 아예 없는 것보다 나쁜 정보가 된다.
- 오타 수정처럼 내용이 달라지지 않는 변경은 갱신하지 않아도 된다. 기준은 **"사용자의 판단이 달라지는가"** 다.
- 한 항목을 고쳤으면 **그 항목의 7개 언어판 날짜를 함께 갱신**한다. 번역이 아직 안 됐다면 그 언어는 옛 날짜로 두는 편이 정직하다.

### 7. 작성 톤과 내용

- 기능 문서와 마찬가지로 사용자를 독자로 상정한다.
- **증상 → 해당 환경 → 원인 → 해결 방법 → 주의할 점 → 언제 없어지나 → 관련 링크** 순서를 기본 뼈대로 삼는다.
- **우회책의 대가를 숨기지 않는다.** 부작용이 있으면 명시하고, 되돌릴 수 있다는 것도 알린다.
- 확인된 환경은 **배포판·버전을 그대로 적는다.** "여러 환경"으로 뭉개면 자기 환경이 해당하는지 판단할 수 없다.
- 우리 코드의 문제가 아닐 때는 **그 사실을 분명히 적되**, 그렇다고 방치한다는 인상을 주지 않는다.

### 8. 작성 책임

- 환경 제약으로 판명된 이슈를 조사했다면, 결론을 이슈 댓글에만 남기지 말고 **트러블슈팅 문서로 옮긴다.** 댓글은 검색되지 않고 묻힌다.
- 새 항목을 추가하면 **모든 언어의 색인과 루트 `README.md`(7종)의 트러블슈팅 챕터 목록에 함께 반영**한다. 언어 하나만 추가하고 끝내지 않는다 — 다른 언어의 전환 줄이 깨진 링크가 된다.
- 문제가 해결되어 문서가 불필요해지면 **삭제하고 색인에서도 뺀다.** 낡은 우회책이 남아 있으면 사용자가 불필요한 설정을 하게 된다.
