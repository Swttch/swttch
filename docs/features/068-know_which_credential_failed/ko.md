# 어떤 자격증명이 거절당했는지 알려준다

> 언어: [English](./en.md) · **한국어**

## 무엇이 문제였나

로그인은 되어 있습니다. 하루 종일 되어 있었습니다. 그런데 채팅이 이렇게 답합니다.

```
● Failed to authenticate. API Error: 401 API key is invalid.
```

무슨 키를 말하는 걸까요. 키를 준 적이 없습니다. 로그인을 했을 뿐입니다.

문제가 정확히 거기 있었습니다. 이 한 줄은 실패했다는 사실과 상태 코드만 말하고,
**어느 자격증명을 제출했는지는 말하지 않습니다.** 그래서 읽는 사람에게 남는 해석은
"나는 분명히 인증되어 있으니 플러그인이 고장난 것"뿐입니다.
[#446](https://github.com/Swttch/swttch/issues/446)이 정확히 그렇게 제보되었고,
제보자는 조금 전까지 터미널에서 같은 CLI를 멀쩡히 쓰고 있었습니다.

그 제보에서 실제로 제출된 자격증명은 IDE가 물려받은 환경에 들어 있던
`ANTHROPIC_API_KEY`였습니다. CLI는 저장된 로그인보다 API 키를 우선하므로 그 키를 썼고,
그 키는 더 이상 유효하지 않았으며, 서버는 401을 돌려보냈습니다. 설계대로 동작했지만,
그 과정이 화면에는 하나도 드러나지 않았습니다.

## 이제 보이는 것

인증에 실패하면 실패 줄 바로 아래에 **CLI가 실제로 사용한 자격증명의 이름**이 붙습니다.

![빨간 실패 줄 "Failed to authenticate. API Error: 401 API key is invalid."와 오른쪽 끝의 Re-Sign 버튼, 그리고 바로 아래에 노란 안내 상자가 "Authenticated with ANTHROPIC_API_KEY, not your Claude login"과 "The server rejected that credential. Remove ANTHROPIC_API_KEY from the environment your IDE inherits and restart the IDE to use your login instead."를 보여주는 채팅 화면](./assets/credential-source-notice.png)

이 이름은 우리가 사용자 컴퓨터를 추측해서 알아낸 값이 아닙니다. CLI가 시작할 때
`system/init` 이벤트의 `apiKeySource` 필드로 직접 알려주는 값이고, 안내는 그 값을 그대로
옮깁니다. 직접 확인하고 싶다면 터미널에서 `claude`를 `--output-format stream-json --verbose`와
함께 실행해 첫 줄을 읽으면 됩니다.

## 안내가 떴을 때 할 일

안내가 뜬다는 것은 API 키가 로그인을 이겼다는 뜻입니다. 상황은 둘로 갈립니다.

**그 키를 쓸 생각이 없었던 경우.** 변수가 설정된 자리를 찾아 제거하고 IDE를
재시작합니다. IDE는 실행되는 순간의 환경을 물려받기 때문에, 셸에서만 지우면 이미 떠 있는
IDE에는 반영되지 않습니다.

| 사용 환경 | 변수가 주로 설정되는 자리 |
| --- | --- |
| macOS, Spotlight/Dock으로 실행 | `~/.zprofile`, `~/.zshenv`, `launchctl setenv` |
| macOS·Linux, 터미널에서 실행 | `~/.zshrc`, `~/.bashrc`, `~/.profile` |
| Linux 데스크톱 세션 | `/etc/environment`, `~/.profile`, `~/.config/environment.d/*.conf` |
| Windows | `setx`, 또는 시스템 속성 → 환경 변수 |

`claude`는 `~/.claude/settings.json`과 `~/.claude/settings.local.json`의 `env` 블록도
읽습니다. 셸에서 찾지 못했다면 두 파일도 확인하세요.

**그 키를 의도적으로 쓰고 있었는데 갑자기 안 되는 경우.** 그렇다면 키 자체가 문제입니다.
폐기되었거나 교체되었거나, 더 이상 접근 권한이 없는 조직의 키입니다. 현재 유효한 키로
교체하세요. API 키는 시간이 지난다고 만료되지 않으므로, 지난주에 되던 키가 오늘 안 된다면
시간이 아니라 서버 쪽에서 무언가 바뀐 것입니다.

## 안내가 뜨지 않는 경우

아래 세 경우에는 일부러 조용히 있습니다. 어느 경우에도 안내가 답이 되지 못하고 소음만
늘리기 때문입니다.

| 경우 | 조용한 이유 |
| --- | --- |
| CLI가 저장된 로그인을 사용함 (`apiKeySource`가 `none`) | 사용자가 이미 그렇게 알고 있는 상태입니다. 이름을 알려줘도 새로운 정보가 없고, 이때의 실패는 로그인 자체의 문제라 옆의 `Re-Sign` 버튼이 답입니다. |
| `system/init`이 아직 도착하지 않음 | 알려줄 값 자체가 없습니다. |
| 실패가 이미 해소됨 | 위쪽에 남아 있는 과거 실패가 이미 지운 변수를 계속 지우라고 조언하면 안 됩니다. 그 실패 **이후에** 성공한 인증 확인이 해소 판정의 기준입니다. |

## 같은 제보에서 함께 고친 것

제보자는 문제를 우회하려고 설정 → CLI 경로에서 CLI 위치를 직접 지정했습니다. 붙여넣은
경로 끝에 공백 한 칸이 딸려 들어갔고, `spawn`은 끝의 공백을 파일 이름의 일부로 취급합니다.

```
spawn /home/u/.local/bin/claude  ENOENT
```

그래서 분명히 맞는 경로가 "찾을 수 없음"이 되었습니다. 이제 경로 설정은 **저장할 때와 사용할
때 양쪽에서** 공백을 제거합니다. 뒤쪽이 중요한 이유는, 수정본을 배포해도 이미 공백이 저장된
설정 파일이 저절로 다시 쓰이지는 않기 때문입니다. **CLI 경로**, **Node 경로**,
**터미널 앱**, **파일 열기 프로그램**, 그리고 사용자 지정 파일 열기 프로그램의 경로가 모두
해당됩니다. 사용자 지정 프로그램의 **인자 템플릿은 입력한 그대로 둡니다.** 명령줄에서 공백은
의미를 가지며, 우리가 손댈 영역이 아니기 때문입니다.

## 한계

**변수가 어느 파일에서 설정되었는지는 알려드릴 수 없습니다.** 우리가 보고할 수 있는 것은
CLI가 무엇을 썼다고 말했는지까지입니다. 변수의 출처를 찾으려고 사용자의 셸 시작 파일을
뒤지는 일은 플러그인이 하지 않으며, 추측해서 알려주는 것은 아무 말도 하지 않는 것보다
나쁩니다. 위의 표가 그 질문에 대한 정직한 답입니다.

**안내는 CLI가 시작한 시점을 말하며, 실패한 시점을 말하지 않습니다.** `apiKeySource`는
시작 시점의 값입니다. CLI는 프로세스당 한 번 자격증명을 결정하므로 실제로는 둘이 일치하지만,
세션 중간에 환경을 바꾸더라도 안내는 실행 중인 프로세스가 집어든 값을 계속 가리킵니다.

**변수를 지운 뒤에는 새 터미널이 아니라 IDE를 재시작해야 합니다.** 프로세스는 시작할 때
환경을 물려받습니다. 운영체제의 규칙이라 플러그인이 우회할 수 있는 부분이 아닙니다.
