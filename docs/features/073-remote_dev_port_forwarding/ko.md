# 이제 원격 개발 환경과 연결해서 사용할 수 있습니다

> 언어: [English](./en.md) · **한국어**

제트브레인의 Remote development 를 통해 ssh 연결을 하고, 원격개발서버에 있는 개발환경을 클라이언트로 접속하는 사용자에게 해당하는 내용입니다.

이전에는 백엔드 연결이 안 되는 상태로 배너만 떠 있었습니다.

이제는 원격 서버 내부에서 구동되는 클로드 코드 동작을 플러그인으로 조작할 수 있습니다.

## 설치 의존성

원격의 개발 서버에 다음 의존성이 설치되어 있어야 합니다.

- **claude 가 설치되어 있어야 하고, 로그인이 되어 있어야 합니다.**
- **확장킷이 설치되어 있어야 합니다.** 버튼 클릭 한 번으로 설치를 완료할 수 있습니다. 설치되어 있지 않아도 동작은 하지만, UI 에서 계정과 사용량과 음성 기능을 다루지 못합니다.

확장킷 설치 버튼은 **설정 → 일반**의 **음성 입력** 섹션 오른쪽 위에 있습니다. 버튼에는 **설치**라고 적혀 있고, 누르면 그 자리에서 설치가 끝납니다. 이미 설치되어 있으면 같은 자리에 버전 번호가 뜨고, 새 버전이 있으면 **업데이트** 버튼으로 바뀝니다.

둘 다 **원격 개발 서버 쪽**에 있어야 합니다. 지금 앉아 있는 컴퓨터가 아닙니다. 플러그인의 백엔드가 원격 서버에서 돌고, `claude` 와 확장킷을 실행하는 것도 그 백엔드이기 때문입니다.

## 무엇이 잘못되어 있었나

채팅 화면은 플러그인이 대신 띄워주는 Node 백엔드가 서빙하는 웹 페이지입니다.
한 대의 컴퓨터에서 쓸 때는 이 사실이 드러나지 않습니다. 화면과 서버가 같은 `localhost` 를 쓰기 때문입니다.

JetBrains 원격 개발에서는 둘이 같은 `localhost` 를 쓰지 않습니다. 백엔드는 원격 호스트에서 돌면서 그곳의 `127.0.0.1:<포트>` 에 귀를 열고, 웹뷰는 지금 앉아 있는 컴퓨터의 JetBrains Client 안에서 돕니다. 웹뷰에게 `localhost` 는 **자기 컴퓨터의 루프백**이고, 거기에는 아무도 귀를 열고 있지 않습니다. 그래서 패널은 껍데기만 그린 다음

> Backend disconnected. Reconnecting…

에서 영영 멈춰 있었습니다 ([#292](https://github.com/Swttch/swttch/issues/292)).

빠져나갈 방법은 SSH 터널을 손으로 뚫는 것뿐이었습니다.

```
ssh -N -L <포트>:127.0.0.1:<포트> 사용자@원격호스트
```

그런데 포트는 백엔드가 시작할 때마다 운영체제가 새로 배정합니다. 그래서 위 명령은 다음 재시작이면 다시 죽어 있었습니다.

더 나쁜 점이 있었습니다. 포트는 웹뷰 URL 의 오리진을 이루는 일부이고 `localStorage` 는 오리진마다 따로 갈립니다. 그래서 포트가 바뀌면 저장해둔 인증 토큰도 함께 길을 잃었고, 그 토큰을 대신할 페어링 코드는 한 번만 쓸 수 있는 값이었습니다.

## 무엇이 달라졌나

사용자가 할 일은 없습니다. 원격 개발 세션에서 패널을 열면 그냥 연결됩니다.

이제 플러그인이 IDE 에게 포트를 대신 열어달라고 요청합니다. 백엔드가 자기가 잡은 포트를 알려오면 `PerClientPortForwardingManager.forwardPort()` 가 그 포트를 연결된 모든 클라이언트에 게시하고, 클라이언트 쪽에 배정된 포트 번호를 되돌려줍니다. 웹뷰 URL 에는 그 포트가 들어갑니다. 트래픽은 IDE 자신의 통로를 타고 흐르므로, 만들 터널도 없고 백엔드가 다시 시작했을 때 다시 만들 것도 없습니다.

프로젝트 단위로 동작합니다. 원격 프로젝트 두 개는 백엔드 두 개를 서로 다른 포트에 띄우는데, 각 포트가 따로 포워딩됩니다.

잘 되고 있는지 확인하려면 지금 쓰는 컴퓨터의 **Port Forwarding** 화면을 여세요. 포워딩된 포트에 **Claude Code** 라벨이 붙어 있습니다. 원격 호스트의 IDE 로그에도 같은 사실이 남습니다.

```
Backend port is reachable from the client on 46655
```

## 달라지지 않는 것

**로컬 IDE 는 아무 영향도 받지 않습니다.** 매니저 목록은 `getServices(..., ClientKind.REMOTE)` 로 풀리는데, 원격 클라이언트가 없으면 이 목록이 비어 있습니다. 그래서 한 대에서 돌아가는 IDE 에서는 조회가 그 자리에서 끝납니다. 포워딩은 일어나지 않고, 웹뷰는 예전과 똑같이 백엔드 자신의 포트를 받습니다.

**실패해도 치명적이지 않고, 조용히 넘어가지도 않습니다.** 예상 밖의 일이 생기면, 이를테면 해당 API 가 아예 없거나 포트 포워딩이 꺼져 있거나 클라이언트가 제때 자기 쪽 포트를 잡지 못하거나 호출이 예외를 던지면, 원래의 호스트 포트로 되돌아갑니다. 로컬에서는 그것이 정답이고, 다른 곳에서도 예전 동작보다 나빠지지 않습니다. 다만 원격 개발에서 호스트 포트는 아무도 귀를 열고 있지 않은 주소이므로, 거기서 되돌아간 경우는 다음 절의 세 가지 방법으로 알려줍니다.

여기서 한 가지는 알고 계시는 편이 좋습니다. **IDE 가 포워딩을 거절하면 플러그인은 그 답을 뒤집지 않습니다.** 플러그인 설정에는 이 동작을 바꾸는 항목이 없습니다.

## 배너가 계속 "Backend disconnected" 라고 말할 때

IDE 는 페이지의 HTTP 는 중계하지만 WebSocket 은 중계하지 않습니다. 그래서 포워딩이 안 된 패널도 껍데기는 그려지는데 연결은 되지 않습니다. 포워딩이 안 된 패널은 백엔드가 죽은 패널과 똑같이 보입니다 ([#473](https://github.com/Swttch/swttch/issues/473)). 둘을 가르는 방법이 세 가지 있습니다.

**배너가 이유를 말해줍니다.** "Backend disconnected. Reconnecting…" 뒤에 이유가 붙습니다.

| 이유 | 뜻 | 할 일 |
|---|---|---|
| `disabled` | 클라이언트에서 포트 포워딩이 꺼져 있습니다 | 클라이언트의 Port Forwarding 화면에서 켭니다 |
| `not-assigned` | IDE 는 포워딩을 받아들였는데 클라이언트가 자기 쪽 포트를 아직 열지 않았습니다 | 할 일 없음. 플러그인이 계속 다시 요청합니다 |
| `api-unavailable`, `failed` | IDE 의 포워딩 API 가 없거나 예외를 던졌습니다 | 원격 호스트의 IDE 로그를 읽습니다 |

**원격 호스트의 IDE 로그에도 같은 이유가 남습니다.** 이런 줄로 시작합니다.

```
Backend port 46655 was not forwarded to the client (disabled)
```

**플러그인이 스스로 다시 요청합니다.** 시간이나 사용자가 풀어줄 수 있는 두 이유(`disabled`, `not-assigned`)에 대해 5초, 15초, 30초, 60초 뒤에 다시 요청합니다. IDE 가 포워딩을 내주는 순간 패널은 그 포트로 다시 불러옵니다. 나머지 두 이유는 다시 요청하지 않습니다. API 가 바뀐 상태는 기다린다고 바뀌지 않기 때문입니다.

**플러그인은 클라이언트의 오고 감도 따라갑니다.** 원격 호스트는 클라이언트가 오고 가는 동안에도 계속 돌고, 포워딩된 포트는 그 포트를 만들어 준 클라이언트의 것입니다. 원격 개발 런처로 시작된 호스트에서는 플러그인이 2초마다 어떤 클라이언트가 붙어 있는지 살피고, 그것이 바뀌면 패널을 다시 불러옵니다. 예전에는 손으로 패널을 다시 열 때까지 "Backend disconnected" 에 갇혀 있던 두 경우가 이렇게 해결됩니다. 둘 다 PhpStorm 2026.2.3 에서 실측했습니다.

- 호스트가 먼저 시작되어 클라이언트가 붙기 전에 패널을 복원하는 경우입니다. 로그에는 `No remote client is connected yet` 이 남습니다.
- 호스트가 계속 도는 동안 클라이언트가 끊겼다가 다시 붙는 경우입니다.

**사이드 패널도 같은 사실을 말합니다.** 사이드 툴 윈도우의 세션 목록에도 같은 배너가 뜹니다. 백엔드에 닿지 못하는 동안에는 "No sessions yet" 이라고 말하지 않습니다. 목록이 도착할 수 없는 상태이지, 기록이 비어 있는 상태가 아니기 때문입니다.

위의 어느 것도 없이 배너가 뜨는 경우가 두 가지 있습니다.

- **원격 호스트의 플러그인이 v0.32.2 보다 오래된 경우입니다.** 포워딩을 요청하는 쪽은 호스트에 설치된 플러그인이므로, 지금 쓰는 컴퓨터의 플러그인이 새 버전이어도 달라지는 것이 없습니다. 원격 호스트의 플러그인을 업데이트하고 그 IDE 를 다시 시작하세요. IDE 는 플러그인에게 반대편 쪽 버전을 읽을 공개된 방법을 주지 않으므로 클라이언트가 스스로 확인할 수는 없습니다. 대신 플러그인이 설치된 JetBrains Client 는 업데이트 뒤 프로젝트를 처음 열 때 한 번, **Swttch runs on the remote host** 라는 알림을 띄웁니다. 알림에는 클라이언트 자신의 버전이 적혀 있고, 호스트도 같은 버전으로 맞추라고 안내합니다.
- **같은 원격 IDE 에 클라이언트 두 대가 붙어 있는 경우입니다.** 포트는 첫 번째 클라이언트에만 포워딩되고, 다른 클라이언트에서 연 패널은 연결되지 않습니다. 플러그인은 패널이 어느 클라이언트의 것인지 알 수 없으므로, 추측하지 않고 이 상황을 로그에 남깁니다.

## 클라이언트에 설치해도 해결되지 않습니다

JetBrains 는 플러그인을 양쪽에 설치하도록 안내하고, 그렇게 하면 문제가 풀린 것처럼 보입니다. 채팅이 연결되고 툴윈도우 아이콘도 나타납니다.

**하지만 해결이 아닙니다.** 그 경우 클라이언트 쪽이 자기 백엔드를 지금 쓰는 컴퓨터에서 띄우고, 그 백엔드는 편집 중인 프로젝트가 아니라 로컬의 빈 폴더를 대상으로 `claude` 를 실행합니다. PhpStorm 2026.2.3 에서 실측한 작업 디렉토리는 `~/Library/Application Support/JetBrains/PhpStorm2026.2/projects/<해시>` 였고, 원격 프로젝트가 아니었습니다.

연결된 것처럼 보이면서 엉뚱한 기계의 파일을 읽는 채팅은 끊겼다고 말하는 채팅보다 나쁩니다. 그래서 클라이언트 쪽은 물러납니다. 백엔드를 띄우지 않고, 툴윈도우도 등록하지 않고, 세션도 복원하지 않고, 상태 위젯도 띄우지 않습니다. 원격 쪽은 그대로이며, 원격의 메뉴 항목은 여전히 화면에 나타납니다.

## 메인테이너를 위한 메모

포워딩 API 는 **리플렉션**으로 접근합니다. 일부러 그렇게 했습니다.

이 API 는 Remote Development 플러그인 안에 있는데, 이 프로젝트가 컴파일 대상으로 삼는 IntelliJ IDEA Community 에는 그 플러그인이 번들되어 있지 않습니다. 컴파일 타임 의존을 걸면 기능이 조용히 빠지는 정도로 끝나지 않고 **빌드 자체가 깨집니다.** 게다가 이 API 는 `@ApiStatus.Experimental` 이라 릴리즈마다 바뀔 수 있습니다. CONTRIBUTING.md 가 바로 이런 상황에 리플렉션을 쓰라고 안내합니다.

이 코드를 고치기 전에 알아둘 API 의 성질이 두 가지 있습니다.

- `forwardPort()` 는 **EDT** 에서 실행되고 있는지를 단언합니다. 패널은 이것을 코루틴에서 호출하므로, API 호출만 EDT 로 넘깁니다.
- 클라이언트 쪽 포트는 **비동기로** 배정됩니다. 그 배정을 기다리는 동안 EDT 를 붙잡고 있으면 안 됩니다. EDT 를 몇 초씩 붙잡으면 IDE 가 얼어붙고, 그것은 지금 고치려는 문제보다 더 나쁜 버그입니다.
