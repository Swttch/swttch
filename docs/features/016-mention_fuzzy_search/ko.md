# `@` 파일 멘션에 퍼지(부분수열) 검색 랭킹 (IntelliJ 스타일)

> 언어: [English](./en.md) · **한국어**
>
> 관련: [#170](https://github.com/Swttch/swttch/issues/170), [#224](https://github.com/Swttch/swttch/pull/224)

## 새로운 점

`@` 파일 멘션 목록이 이제 **퍼지(부분수열) 매칭**으로 결과를 순위화합니다.
IntelliJ의 Search Everywhere / CamelHump와 같은 방식입니다. 이전에는 입력한
검색어가 경로 안에 **연속된 부분 문자열**로 나타날 때만 매칭돼서, `bcva` 같은
축약어로는 아무것도 찾지 못했습니다.

이제 `@bcva`가 `docs/business-case-validation-architecture.md`를 찾습니다 —
각 글자가 **단어 경계** 하나씩에 대응합니다
(**b**usiness-**c**ase-**v**alidation-**a**rchitecture). 그리고 매칭된 글자가
드롭다운에서 강조 표시돼, 왜 그 항목이 걸렸는지 눈으로 확인할 수 있습니다.

## 사용자가 보는 것

- **축약어가 동작합니다.** `@jbadapter`가 `JetBrainsAdapter.ts`를, `@brad`가
  `BrowserAdapter.ts`를 매칭합니다. 검색어의 글자는 붙어 있지 않아도 되고,
  순서만 맞으면 됩니다.
- **매칭된 글자가 강조**됩니다(굵게·강조색). IntelliJ Search Everywhere처럼
  표시돼 매칭 지점이 한눈에 보입니다.
- **가장 좋은 매칭이 위로 옵니다.** 단어 경계(카멜케이스 대문자, 그리고
  `/`, `-`, `_`, `.`, 공백 구분자)에서의 매칭과 파일 자체 이름에서의 매칭이,
  흩어진 매칭이나 디렉토리 경로로만 걸린 매칭보다 위에 랭크됩니다.

## 동작 방식

백엔드가 기존의 부분 문자열 필터를 **부분수열 스코어러**로 교체했습니다
(`listProjectFiles.ts`의 `rankFiles`):

- 검색어의 모든 글자가 대상 안에 **순서대로** 나타날 때만 후보로 매칭되고,
  아니면 제외됩니다.
- 매칭된 각 글자는 매칭 시작, **단어 경계**(카멜케이스 대문자, 또는
  `/ _ - . `·공백 바로 뒤) 안착, 직전 매칭과의 **연속**에 대해 보너스를 받고,
  매칭 사이의 간격에는 감점이 붙습니다. 이것이 `b`·`c`·`v`·`a`가 우연히 흩어진
  파일보다 `business-case-…`를 위로 밀어 올리는 이유입니다.
- 각 항목은 **basename(파일명)을 먼저**(보너스 포함) 그리고 전체 상대 경로에
  대해 점수를 매겨, 자기 이름이 매칭되는 파일이 디렉토리 경로로만 매칭되는
  파일보다 위에 랭크됩니다. 동점이면 더 짧은 경로가 우선입니다.

각 결과와 함께 백엔드는 매칭된 글자의 위치인 `matchIndices`를 반환하고, 웹뷰는
이를 **편집 없이 그대로**(원본 데이터 보존) `MentionDropdown`으로 전달하며,
거기서 `renderHighlightedPath`가 정확히 그 글자들만 감쌉니다. 빈 검색어는 기존과
동일하게 디렉토리만 반환합니다.
