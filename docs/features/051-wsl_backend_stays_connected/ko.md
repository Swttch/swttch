# WSL2에서 백엔드가 10초마다 끊기지 않습니다

> 언어: [English](./en.md) · **한국어**

## 무엇이 문제였나

Windows 11에서 WSL2 안의 프로젝트를 열면 채팅이 이런 상태에 빠졌습니다.

```
Backend disconnected. Reconnecting...
```

접속은 됩니다. 10초쯤 정상으로 동작합니다. 그리고 끊깁니다. 다시 붙습니다. 또 10초 뒤 끊깁니다.

IDE는 그동안 한 번도 닫히지 않았고, 터미널의 `claude` 명령은 멀쩡히 동작했습니다.

제보자 두 분이 각각 다른 기계에서 같은 증상을 겪었고, 그중 한 분은 VS Code로 옮겨 가야 했습니다.

이 문제는 [#384](https://github.com/Swttch/swttch/issues/384)로 제보되었습니다.

플러그인 0.29.3과 0.29.4가 영향을 받았습니다.

## 왜 벌어졌나

백엔드에는 **자기를 띄운 호스트가 죽으면 자기도 끝내는** 장치가 있습니다.

이 장치는 [#360](https://github.com/Swttch/swttch/pull/360)에서 들어왔습니다. IDE를 닫았는데도 백엔드가 살아남아 포트와 파일을 붙들고 있으면, 새로 설치한 버전이 뜨지 못해 Windows를 재부팅해야 했기 때문입니다([#308](https://github.com/Swttch/swttch/issues/308)).

그 장치는 IDE의 프로세스 번호(pid)를 받아 10초마다 "아직 살아 있나"를 물었습니다.

그런데 **WSL2에서는 IDE와 백엔드가 서로 다른 세계에 삽니다.**

IDE(PhpStorm)는 Windows 프로세스이고, 백엔드는 WSL2 리눅스 배포판 안의 프로세스입니다.

리눅스 안에서 Windows의 프로세스 번호를 물으면 **그런 프로세스는 없다**는 답이 돌아옵니다. 죽어서가 아니라, 애초에 리눅스에서 볼 수 있는 번호가 아니어서입니다.

백엔드는 그 답을 "호스트가 죽었다"로 읽었습니다.

그래서 접속하고 정확히 10초 뒤, 첫 확인에서 멀쩡히 떠 있는 PhpStorm을 죽었다고 판정하고 스스로 종료했습니다.

제보자가 남긴 로그가 이 순서를 그대로 보여줍니다.

```
[node-backend] Host process 14056 died — shutting down
[node-backend] parent-death received, shutting down...
RPC WebSocket closed: 1006
```

그리고 같은 제보자가 WSL2 안에서 Windows 쪽에 직접 물어, 14056번이 **그 시각 내내 살아 있었다**는 것을 확인해 주셨습니다.

## 어떻게 고쳤나

두 가지를 함께 고쳤습니다.

### 볼 수 없는 것을 죽었다고 하지 않습니다

백엔드는 호스트가 방금 자기를 실행시켜서 존재합니다. 그러니 **시작하는 순간에 호스트가 죽어 있을 수는 없습니다.**

그 순간에 "그런 프로세스 없음"이 나온다면, 그것은 죽었다는 뜻이 아니라 **여기서는 볼 수 없는 번호**라는 뜻입니다.

이제 백엔드는 감시를 시작할 때 한 번 확인해 보고, 볼 수 없는 번호면 **번호로 묻는 것을 아예 하지 않습니다.**

답할 수 없는 질문에 틀린 답을 내놓는 대신 묻지 않기로 한 것입니다.

Windows에서 WSL 없이 쓰는 경우에는 IDE와 백엔드가 같은 세계에 있으므로 이 확인이 통과하고, 감시는 전과 똑같이 동작합니다.

### IDE는 번호 대신 연결로 지켜봅니다

번호로 묻는 것을 그만두면 WSL2에서는 아무도 호스트를 지켜보지 않게 됩니다. 그러면 #308이 다시 일어날 수 있습니다.

그래서 IDE만큼은 **번호가 아니라 연결**로 지켜보게 했습니다.

IDE는 살아 있는 내내 백엔드와 전용 연결 하나를 붙잡고 있습니다. IDE가 어떤 이유로든 사라지면 그 연결은 운영체제가 끊어 줍니다.

이 방식에는 앞의 문제가 없습니다. 두 프로세스가 같은 세계에 있어야 할 이유도, 사이에 낀 다른 프로그램에 가려질 이유도 없습니다.

연결이 끊기면 곧바로 종료하지는 않습니다. IDE를 재시작하면 연결이 한 번 끊겼다가 새로 붙기 때문입니다.

**15초를 기다리고, 그 안에 다시 붙지 않으면** 그때 호스트가 사라진 것으로 봅니다.

## 무엇이 달라지지 않았나

[#360](https://github.com/Swttch/swttch/pull/360)이 세운 규칙은 그대로입니다.

**백엔드를 띄운 쪽이 사라지면 백엔드도 끝납니다.** 브라우저나 터널로 누가 붙어 있어도 마찬가지입니다.

채팅 연결은 IDE 전용 연결과 다른 연결이라, 채팅창이 열려 있다는 이유로 판정이 달라지지 않습니다.

터미널에서 `ccg`로 띄운 경우에는 IDE 전용 연결이 아예 없으므로, 전과 똑같이 동작합니다.

버전 관리 도구(Volta, nvm, fnm)를 쓰는 경우도 전과 똑같이 동작합니다. [#360](https://github.com/Swttch/swttch/pull/360)이 그 경우를 위해 넣은 처리는 Windows에서 그대로 유지됩니다.

## 어떻게 확인했나

**실제 Windows 11 노트북의 WSL2에서 재현하고, 고쳐진 것을 확인했습니다.**

살아 있는 Windows 프로세스(`explorer.exe`)의 번호를 백엔드에 호스트로 건네고, 그 번호가 배포판 안에는 존재하지 않는다는 것을 먼저 확인했습니다. 제보자들이 겪은 상황과 같은 조건입니다.

| 시각 | 고치기 전 (배포된 0.29.4) | 고친 뒤 |
|---|---|---|
| 5초 | 살아 있음 | 살아 있음 |
| 12초 | **죽음** | 살아 있음 |
| 18초 | | 살아 있음 |
| 25초 | | 살아 있음 |

고치기 전이 죽은 이유는 로그에 그대로 남았습니다.

```
[node-backend] Host process 9328 died — shutting down
```

그 시각에 9328번은 멀쩡히 살아 있었습니다.

고친 뒤에는 확인 주기를 두 번 넘길 때까지 살아 있었고, 저희가 직접 종료 신호를 보내 끝냈습니다.

백엔드 테스트 1774개도 전부 통과합니다.

이번 문제를 재현하는 테스트를 새로 넣었고, **고친 코드를 다시 무력화하면 그 테스트가 정확히 실패하는 것**을 확인했습니다. 통과가 의미를 갖는지 먼저 확인한 것입니다.
