# 기능 문서 색인 (Feature Docs Index)

이 폴더는 사용자를 독자로 한 **기능 설명서**들을 모아둔다. 작성 규칙은 [docs/CLAUDE.md](../CLAUDE.md)를 따른다.

각 기능은 `NNN-feature_name/` 폴더로 관리하며, 폴더 안에 언어별 번역본(`en.md`, `ko.md`, …)을 둔다.

Scheduled Messages 엔진 위에 만들어져 리셋 시각에 "continue"를 예약하고, 백엔드 게이트가 전송 직전 사용량을 재확인(5초 폴링·최대 10분, 네트워크 오류 시 사람이 읽을 수 있는 사유로 중단)해 실제 충전된 뒤에만 발사한다. 한도 배너의 예약/즉시 재개 버튼, 설정 → General의 기본값 토글(세션별 오버라이드 가능)을 제공하며, 리셋 시각은 CLI 한도 안내 문구에서 직접 파싱(공식/미문서 API 비의존) (`feat/auto-resume-on-limit-reset` 브랜치)
- [Models you connect yourself now show by their own name](./021-custom_model_catalog_display/en.md) — Opus/Sonnet/Haiku 자리에 직접 연결한 모델(`ANTHROPIC_DEFAULT_*_MODEL`)을 쓸 때, 대화를 시작하면 입력창 아래 표시와 모델 선택 패널이 **Default** 로 되돌아가고 그 자리에 들어간 긴 문장이 줄을 두 줄로 무너뜨리던 문제를 수정. 근본 원인은 이름을 못 알아본 것이 아니라 **"못 알아봤다"를 "기본값이다"로 단정**해 사용자 선택을 버린 것 — 이제 식별에 실패하면 폴백하지 않고 **기존 선택을 그대로 유지**한다(다음 요청도 그 모델로 나감). 이름 형태에 의존하지 않는 규칙이라 GLM 외 임의 커스텀 모델에도 대응. 부수적으로 식별 성공률도 높임(설명의 `Custom Haiku model` 활용, 접미사·대소문자 흡수)하고, 끝내 모르는 모델은 Default 인 척하지 않고 원본 값 그대로 표시. 입력창 아래 줄은 좁은 폭에서도 한 줄 유지 + 말줄임(권한·사용량 표시 포함) ([#217](https://github.com/Swttch/swttch/issues/217), [#202](https://github.com/Swttch/swttch/issues/202))
- [@ file mentions now work inside slash commands](./020-mention_inside_slash_command/en.md) — 슬래시 명령을 입력하는 중에 `@` 를 쳐도 파일 선택 목록이 뜨지 않던 문제를 수정. 슬래시 패널과 파일 목록이 입력창 위 같은 자리를 공유하는데 판단 기준이 "줄이 `/` 로 시작하나"뿐이라, 검색이 끝난 목록이 패널에 계속 가려져 있었다(바깥을 클릭하면 잠깐 보였다가 다음 글자에 다시 가려짐). 기준을 "커서가 `@토큰` 안에 있나"로 바꿔 두 기능이 자리를 나눠 쓰게 했고, 파일 선택 후 슬래시 패널 복귀·커서 되돌림 시 목록 재표시·이메일 주소 오작동 방지를 함께 정리. 스킬 전용 문제가 아니라 모든 슬래시 명령에 해당 ([#236](https://github.com/Swttch/swttch/issues/236))

- [Long lines fold so you can read them at a glance](./036-soft_wrap/en.md) — 고정폭 블록(Edit diff 카드·도구 `IN`/`OUT`·AskUserQuestion 기록 카드)이 줄을 접지 않아 **긴 줄이 카드 폭에서 잘리고 가로 스크롤로만 도달**됐다. diff에서는 지운 줄/넣은 줄이 붙어 있는데 정작 달라진 부분이 잘린 뒤쪽이면 무엇이 바뀐지 알 수 없었다. `설정 > 모양`에 **자동 줄바꿈**(`softWrap`, 기본 off) 토글을 넣고 `pre-wrap`+`break-all`로 접는다(경로·JSON은 공백이 없어 단어 경계만으로는 여전히 넘침). 값을 각 컴포넌트가 읽지 않고 **`<html>`에 `.soft-wrap` 클래스 하나만 토글**해 CSS가 보게 했다 — 대상 블록이 열 곳 넘게 흩어져 있어 구독·prop을 그만큼 늘리지 않으려는 것(대신 연결이 끊겨도 화면은 멀쩡해 보이므로 클래스 토글 자체를 테스트로 고정). 함께 고친 두 번째 제보가 **배경색이 텍스트 끝까지 안 감**인데, 이건 **랩과 무관하게 항상 적용**된다(기본값이 off라 끈 상태에서도 맞아야 함). 원인은 diff 행이 가로 스크롤 `<pre>` 안의 블록이라 **폭이 부모의 콘텐츠 박스=보이는 폭으로 풀리는 것**. 함정: ① 행마다 `width:fit-content`를 주는 건 **오답** — 각 행이 자기 텍스트 길이만 가져 한 카드에서 1227~4704px로 제각각이 되고 행마다 다른 지점에서 tint가 끊긴다(고쳤다고 보고했다가 사용자가 화면에서 잡아냄) ② 행에 `min-width:max-content`도 안 됨 — 블록 자식은 부모 콘텐츠 박스 기준이라 보이는 폭으로 풀린다. 정답은 `<pre>` 안에 **`min-width:max-content` 래퍼(`.diff-body`)를 두고 행이 `min-width:100%`로 그것을 채우는 것**(래퍼는 `.soft-wrap`에서 `min-width:0`으로 되돌려야 접힘) ③ 검증에서 **프로브 한 줄만 재면 이 결함은 관찰 자체가 불가** — 값이 아니라 `new Set(widths).size === 1` 같은 **행들 사이의 관계**를 단언해야 한다. jsdom은 레이아웃을 안 하므로 CSS 원문(`?raw`)을 읽어 `fit-content` 재유입을 막는 테스트를 함께 둠. 부수 정리로 `모양` 첫 섹션의 "테마" 제목 제거(`SettingSection`의 `title`을 옵셔널화 — 화면 이름이 이미 "모양"이라 바로 아래 "테마"는 한 줄을 쓰며 구분을 못 함) ([#179](https://github.com/Swttch/swttch/issues/179))

- [MCP servers run through Docker no longer pile up containers](./049-mcp_docker_container_leak/en.md) — `docker run`으로 도는 MCP 서버가 **패널을 새로고침할 때마다 컨테이너를 두 개씩 남기던** 것을 수정([#363](https://github.com/Swttch/swttch/issues/363), 제보자는 반나절에 67개·4.2GB). `--rm`이 붙어 있어도 소용없었던 이유는 우리가 붙잡은 것이 컨테이너가 아니라 **`docker` 클라이언트**여서다 — stdin 닫기·SIGTERM·SIGKILL 세 단계가 전부 클라이언트에게 가고, 컨테이너 안 PID 1이 EOF로도 SIGTERM으로도 안 죽으면 셋 다 살아남으며 `--rm`은 **컨테이너가** 끝나기를 기다리는 옵션이라 영영 발동하지 않는다. Docker는 누가 띄웠는지도 기록하지 않아(클라이언트를 죽이기 전후 `docker inspect`에 **바뀌는 필드가 하나도 없다**) 나중에 고아를 알아볼 방법이 없으므로, 소유권을 **띄울 때 미리 적어두는** 구조로 갔다. 세 갈래로 해결했다 — ① 상태 조회가 매번 `claude mcp list`/`mcp get`으로 CLI를 새로 부팅해 서버를 두 번 더 띄우던 것을, **이미 떠 있는 CLI에게 묻는** 방식으로 바꿔 새로고침당 신규 컨테이너를 0으로 만들었다(덤으로 **사용자의 채팅이 실제로 붙어 있는 프로세스의 상태**를 보여주게 되어 정확해졌고, 도구 목록도 같은 답변에 와서 상세 화면이 다시 접속하지 않는다. 물어볼 CLI가 없으면 공식 명령으로 그대로 폴백한다) ② Fable 가용성 점검처럼 **MCP가 필요 없는** 프로브는 서버를 아예 안 읽게 했다 ③ 정말로 서버가 필요한 경로는 spawn 직전과 **CLI 프로세스 종료 시**의 차집합 중 설정의 이미지·실행인자가 정확히 일치하는 것만 회수한다 — 기준을 세션이 아니라 **프로세스**로 잡은 이유는 한 세션이 여러 CLI보다 오래 살고(파이프 끊김·`--resume`·권한모드 변경) 그때마다 컨테이너가 하나씩 더 생기기 때문. 백엔드가 강제 종료돼 회수 코드가 못 도는 경우까지 막으려고 각 채팅 CLI가 자기 컨테이너 id를 레지스트리에 **미리 기록**하고 다음 부팅의 고아 스윕이 치우며, **살아 있는 다른 백엔드 소유 기록은 건드리지 않는다**. 설정에 docker MCP 서버가 없으면 코드가 실행조차 되지 않고, docker가 없거나 판단이 서지 않으면 항상 **지우지 않는 쪽**으로 실패한다
- [Your settings file can no longer be wiped](./050-settings_never_wiped/en.md) — 사용자의 `~/.claude/settings.json`이 **20개 키에서 3개로 줄어든** 사고를 수정([#386](https://github.com/Swttch/swttch/issues/386)). `mcpServers`·`statusLine`·`enabledPlugins`·`env` 등 **저희가 만들지도, 되살릴 수도 없는 사용자 자산**이 사라졌고, 제보자는 한참 뒤 커밋에 공동 작성자 줄이 붙는 것을 보고서야 알았다(`includeCoAuthoredBy: false`가 사라진 키 중 하나였다). 원인은 **두 결함이 겹쳐 증폭**된 것이다 — ① `writeKeyToJsonFile`이 `writeFile`로 저장해 **truncate 후 쓰기가 원자적이지 않았고**, 여러 백엔드(워크트리 dev 서버·standalone `ccg`·IDE 플러그인)가 같은 파일을 쓰므로 겹치면 짧은 payload 뒤에 긴 쪽의 꼬리가 남아 JSON이 깨진다. ② `readJsonFileSafe`가 **파싱 실패를 `{}`로 답했다** — 리더에겐 타당하지만 read-modify-write의 읽기 반쪽으로 쓰면 파괴적이라, 다음 저장이 그 빈 객체 위에 키 하나를 얹어 **읽지 못한 파일을 한 키짜리 파일로 다시 태어나게** 한다(남아 있던 3개는 재탄생 뒤 GUI가 저장한 것). 즉 **드문 사고 하나가 확정적 전체 삭제로 증폭**되며, 경합이 끝난 뒤에도 회복되지 않는다. `atomic-json.ts` 하나로 세 가지를 세우고 같은 결함이 있던 경로를 전수 전환했다: **temp+rename 원자적 쓰기**(임시 파일은 반드시 같은 디렉토리의 형제 — `rename`은 파일시스템 안에서만 원자적이라 `os.tmpdir()`은 다른 볼륨일 수 있다. 교체되는 파일의 **권한 비트를 stat→chmod로 이어받는다** — rename은 내용이 아니라 파일 자체를 갈아끼워서, 없으면 사용자가 600으로 잠근 파일이 umask 기본으로 돌아온다. Windows는 AV·인덱서가 대상을 쥐고 있을 때 EPERM/EBUSY가 나므로 짧은 백오프로 3회 재시도), **"읽을 수 없음"과 "비어 있음"의 분리**(`readJsonForUpdate`가 두 경우를 다른 값으로 답하고, 파싱 실패면 저장을 **거부하고 파일을 건드리지 않는다** — 0바이트 파일만 예외로 `ok`다. 지킬 내용이 없어 덮어써도 잃는 것이 없고, 거부하면 저장만 영영 막히기 때문. 파일은 디스크 포화·강제 종료·다른 도구로도 깨지므로 **원인과 무관하게 우리가 지우는 쪽이 되지 않는 것**이 이 가드의 목적), **경로별 쓰기 직렬화**(resolve된 경로마다 체인 — 우리 프로세스 안의 read-modify-write끼리는 절대 겹치지 않는다). 적용: `~/.claude/settings.json`·`settings.local.json`, `~/.claude.json`(MCP 비활성 목록 — 사용자의 전 프로젝트 기록이 든 최대 자산 파일), 프로젝트 `.claude/settings*.json`, 프로젝트 `.claude-code-gui/settings.json`(`catch { /* start fresh */ }`가 정확히 그 wipe를 하고 있었다), 세션 제목 오버라이드, `profile.json`, `license.json`. `settings.ts`에 따로 있던 `atomicWriteFile`도 지우고 공용 모듈로 합쳤다. **실측**: 별도 프로세스 4개 × 25회 × 5시행에서 고치기 전 **0/5**(매 시행 원본 키 전부 소실 — 이슈 그대로 재현), 고친 뒤 **5/5**(전부 보존). 테스트가 결함을 실제로 잡는지는 **가드를 무력화해 5개가 정확히 실패하는 것**으로 확인했다. **남는 것**: 서로 다른 백엔드 프로세스가 read-modify-write 창(중앙값 1.09ms) 안에서 정확히 겹치면 상대가 그 순간 새로 추가한 키가 밀린다 — 파일이 깨지지도, 기존 키가 사라지지도 않으며 다시 저장하면 반영된다. 같은 백엔드의 클라이언트끼리는 직렬화로 **동시 200쌍에서 손실 0회**이고, 순차 저장은 애초에 해당 없다(뒤에 저장하는 쪽이 앞의 결과를 읽는다). `claude` CLI 자신도 같은 방식이라 원래부터 있던 성질이고, 없애려면 파일 락이 필요해 이번에는 넣지 않았다
- [The backend no longer drops every ten seconds on WSL2](./051-wsl_backend_stays_connected/en.md) — WSL2 프로젝트에서 채팅이 **접속 후 정확히 10초마다 끊기고 다시 붙기를 무한 반복하던** 것을 수정([#384](https://github.com/Swttch/swttch/issues/384), 제보자 두 분이 각각 다른 기계에서 겪었고 한 분은 VS Code로 옮겨 갔다). 0.29.3에서 들어간 회귀다. 원인은 [#360](https://github.com/Swttch/swttch/pull/360)이 넣은 **호스트 사멸 감시가 프로세스 번호(pid)로 묻는다**는 데 있다 — WSL2에서는 IDE가 Windows 프로세스이고 백엔드는 배포판 안의 리눅스 프로세스라 **번호가 통하는 세계 자체가 다르다.** 리눅스에서 Windows pid를 물으면 항상 `ESRCH`(그런 프로세스 없음)가 돌아오는데, 감시 코드가 그것을 **죽음으로 읽어** 첫 확인(10초)에서 멀쩡히 떠 있는 PhpStorm을 죽었다고 판정하고 스스로 종료했다. 제보자가 WSL2 안에서 Windows 쪽에 직접 물어 해당 pid가 **그 시각 내내 살아 있었다**는 것까지 확인해 주셨다. 두 갈래로 고쳤다 — ① **"볼 수 없음"을 "죽음"으로 읽지 않는다**: 백엔드는 호스트가 방금 실행시켜서 존재하므로 **시작 순간에 호스트가 죽어 있을 수 없고**, 그 순간의 `ESRCH`는 죽음이 아니라 **여기서 관측 불가능한 번호**라는 뜻이다. 이제 감시를 무장할 때 한 번 확인해 보고 관측 불가면 **번호로 묻는 것을 아예 무장하지 않는다**(답할 수 없는 질문에 틀린 답을 내놓는 대신 묻지 않는다). Windows 네이티브는 호스트와 백엔드가 같은 pid 네임스페이스라 이 확인이 통과해 **전과 동일하게 무장**되며, `CCG_HOST_PID`가 애초에 도입된 Volta/nvm/fnm shim 경로도 그대로다(shim은 **어느 pid를 보는지**를 바꿀 뿐 **볼 수 있는지**를 바꾸지 않는다) ② **IDE 호스트는 번호가 아니라 연결로 지켜본다**: 번호 감시를 끄면 WSL2에서 아무도 호스트를 안 보게 되어 #308이 재발하므로, IDE가 살아 있는 내내 붙잡고 있는 `/rpc` 소켓의 소멸을 호스트 사멸로 읽는다 — 소켓은 **같은 pid 네임스페이스를 요구하지 않고**, 사이에 낀 shim이 가릴 수도 없으며, IDE가 어떻게 죽든 커널이 닫아 준다. 끊김 즉시 종료하지는 않는다(IDE 재시작은 끊었다가 새 소켓으로 돌아오므로) — **15초 안에 재접속이 없을 때만** 사멸로 판정한다. #360이 세운 규칙은 그대로 유지된다: **띄운 쪽이 사라지면 브라우저·터널 클라이언트가 붙어 있어도 백엔드는 끝나고**, 채팅용 `/ws`는 별도 소켓이라 판정에 들어가지 않으며, `/rpc`를 열지 않는 터미널(`ccg`) 호스트는 SIGHUP + pid 폴러 경로 그대로다. **검증**: **실제 Windows 11 노트북의 WSL2에서 재현하고 고쳐진 것을 확인했다** — 살아 있는 `explorer.exe`(pid 9328)를 호스트로 넘기고 그 pid가 배포판 안에 없음을 먼저 확인한 뒤, 배포된 0.29.4 번들은 **12초에 `Host process 9328 died`를 찍고 죽었고** 수정본은 두 폴링 주기를 넘겨 25초까지 살아남았다(대조군이 버그를 재현하는 것을 먼저 확인했기에 결과가 의미를 갖는다 — 첫 시행에서 번들 복사가 빠져 둘 다 5초에 죽었고, 대조군 조건이 없었으면 "수정본도 죽는다"고 오판할 뻔했다). 백엔드 1774개 전부 통과했고, 가드를 무력화하면 재현 테스트가 정확히 실패하는 것도 확인한 뒤 원복했다
- ["Stop asking me for every edit" now works](./052-stop-asking-for-every-edit/en.md) — 플랜을 **"예, 자동 승인"**으로 승인하고도 **이어지는 편집마다 승인 요청이 떠서** 수백 번을 눌러야 했던 것을 수정([#393](https://github.com/Swttch/swttch/issues/393), 제보자는 대안으로 "CLI를 쓴다"고 적었다). 서로 다른 결함 넷이 하나의 경험으로 합쳐진 것이었고, **UI가 제시한 탈출구가 전부 아무 일도 하지 않았다.** ① **고른 모드가 실행 중인 CLI에 닿지 않았다** — `--permission-mode`는 spawn 시점 플래그라 모드 변경은 다음 메시지의 재시작으로만 전달됐고, Claude가 작업하는 동안에는 무엇을 눌러도 화면 라벨만 바뀌었다. 이제 살아 있는 CLI에 `set_permission_mode`를 보내 그 턴의 남은 편집부터 적용한다(미문서화 subtype이라 **보조 최적화로만 쓰고**, 받지 않으면 기존 재시작 경로가 그대로 받는다 — `readReportedMode`가 CLI가 통보한 모드를 채택하므로 폴백에 추가 코드가 필요 없다) ② **플랜 승인의 "자동 승인"이 라벨만 바꿨다** — `setInputMode`가 로컬 상태만 건드렸고 CLI에는 모드 언급이 없는 평범한 승인만 갔다. 이제 같은 경로를 타며, CLI 자신의 플랜 승인 모드 변경이 우리 전환을 덮지 않는 것을 실측으로 확인했다 ③ **"예, 이번 세션에서 모든 편집 허용"을 CLI에 알리지 않았다** — 웹뷰가 도구 이름을 ref에 담아두고 이후 요청에 대신 답하는 방식이라 **CLI는 계속 물었고 질문이 답해진 게 아니라 가려졌으며**, 렌더가 바뀌면 사라졌고, 마침 물어본 도구 하나에만 걸렸다(Claude는 `Edit`·`Write`·`MultiEdit`·`NotebookEdit`를 번갈아 쓴다). 이제 문서화된 `updatedPermissions`로 승인과 함께 보내 **CLI가 스스로 묻지 않게** 되고, ref와 세션 전환 시 초기화와 조용한 자동 승인 분기를 **전부 삭제**했다. 편집 도구는 편집 계열 전체를 허용하고 그 외 도구는 자기만 허용해 **"모든 명령어 허용"이 이웃으로 넓어지지 않는다** ④ **두 diff 리뷰 어디에도 탈출구가 없었다** — 수백 번 Apply를 누르던 제보자가 IDE 리뷰 바에서 찾은 것은 `Clear all`이었고 그것을 탈출구로 읽었는데 **실제로는 체크를 전부 해제하는 정반대 버튼**이다. 두 리뷰 모두 `Allow all edits` 버튼을 갖게 했고, 열린 요청을 `Apply`와 똑같이 답하면서 세션 규칙을 함께 건다(IDE에서는 이 diff를 답하는 버튼들과 떨어뜨려 **왼쪽 정렬**). **검증**: 브라우저와 샌드박스 IDE에서 두 리뷰 화면 모두 실측했고, 버튼을 누른 뒤 **두 번째 파일이 승인 없이 쓰이는 것**과 **Bash는 여전히 묻는 것**을 확인했다. 백엔드 1779개·웹뷰 2872개 통과했고, 모드 전달을 무력화하면 신규 테스트가 정확히 실패하는 것도 확인한 뒤 원복했다. **남은 한계**: 승인 요청이 떠 있는 동안에는 입력창이 가려져 모드 선택기에 손이 닿지 않는다
- [Up and Down walk the prompts you typed](./053-prompt_history_in_the_composer/en.md) — 입력창에서 위 화살표를 눌러 이전 프롬프트를 꺼내는 기능을 실제로 쓸 수 있게 고쳤다. **다시 연 대화에서는 대개 아무것도 나오지 않았다** — 히스토리를 채팅 화면이 들고 있는 대화 기록에서 만들었는데 그것은 한 페이지, 최신 **엔트리** 50개뿐이고 엔트리는 대개 프롬프트가 아니기 때문이다(이 저장소 대화 119개 실측: 사람이 친 프롬프트 3,190개 중 최신 페이지 안에 든 것은 129개 **4%**, 가장 큰 대화는 프롬프트 193개 중 **0개**). 이제 대화 전체를 들고 있는 백엔드에 물어보며, 한 번에 20개씩 받고 거슬러 올라가면 이어서 받는다(프롬프트에는 붙여넣은 것이 그대로 실려 있어 100개를 한 번에 보내면 최악의 대화가 **21MB** — 이미지 블록을 빼는 것은 원본 데이터 보존 원칙이 금지하는 엔트리 편집이므로 **개수가 아니라 범위를 자른다**). 함께 고친 것 셋 — ① **CLI가 쓴 글이 입력창에 들어오던 것**(9,326줄 대화 하나에서 `user` 엔트리 1,345개 중 1,281개가 도구 결과이고 사람이 친 것은 46개 남짓): CLI가 표시해두는 엔트리는 플래그로, `<command-name>` 전개·명령 출력·중단 표시·`<task-notification>`처럼 **아무 플래그도 없는 것**은 내용으로 걸러낸다(`permissionMode`는 CLI가 **처리한** 프롬프트에 붙는 것이라 CLI 자신이 주입한 것에도 붙는다 — 그래서 받아들이는 근거가 아니라 걸러내는 근거로만 쓴다) ② **응답 중에 쳐서 큐에 들어간 메시지가 통째로 빠지던 것**: CLI가 그런 메시지는 `user` 엔트리로 아예 쓰지 않고 큐 기록만 남기기 때문으로, 채팅 기록이 말풍선을 되살릴 때 쓰던 짝짓기 규칙을 `shared/`로 올려 **두 곳이 같은 함수를 쓰게** 했다(화면에 보이는데 히스토리엔 없는 메시지가 생길 수 없다) ③ **긴 프롬프트에서 커서가 어디 있든 곧장 이전 프롬프트로 건너뛰던 것**: 줄바꿈 문자를 찾는 방식이라 폭에 맞춰 접힌 한 문장은 모든 줄이 "첫 줄"로 판정됐다 — `utils/domSelection`이 Cmd+화살표에서 같은 이유로 이미 걷어낸 방식이었다. 이제 **커서가 맨 첫 글자(아래는 맨 끝 글자)에 닿았을 때만** 히스토리로 넘어가고, 불러온 프롬프트는 걸어가던 방향의 끝에 커서를 놓아 연타가 이어진다. 방금 보낸 프롬프트는 CLI가 기록하기 전에도 즉시 잡히고, 입력창을 비우면 걷던 위치가 처음으로 돌아간다. **남긴 한계**: 같은 프로젝트의 다른 대화 프롬프트는 내놓지 않으며(CLI 터미널 히스토리는 넘나들지만 지금 안 보는 대화의 문장이 튀어나오는 것은 도움보다 놀라움에 가깝다는 판단), 슬래시 명령은 대화 기록에 XML 전개형으로 저장돼 있어 뺐다 (자체 기획)
