# MCP 서버 목록 조회에 미문서화 `control_request{subtype:"mcp_status"}`를 쓴다

> 마지막 갱신: 2026-09-02
> 수정 이력은 이 파일을 고쳐 적지 말고 `git log -- docs/principle-exceptions/363-mcp-status-control-request.md`로 확인한다.

- 관련 이슈: [#363](https://github.com/Swttch/swttch/issues/363)
- 관련 PR: [#388](https://github.com/Swttch/swttch/pull/388)

## 어떤 원칙을 위반하는가

`CLAUDE.md`의 **★ 핵심 원칙** 중 두 곳이다.

**2번 「공식 지원 비의존」** — "미문서화 내부 프로토콜에 의존하지 않는다".

**3번 「참고 대상은 UX만 모방한다」** — 이 항목은 하필 **이 사례를 금지 예시로 명시**하고
있다. "Cursor가 MCP 상태 조회에 미문서화 `control_request{subtype:"mcp_status"}` 내부
프로토콜을 쓰더라도, 우리는 그 화면을 공식 `claude mcp list` 명령으로 구현한다."

우리는 그 문장이 하지 말라고 한 것을 한다. 원칙 문장은 고치지 않았고, 여기 예외로 남긴다.

## 어느 기준으로 예외가 되는가

[README](./README.md)의 세 기준 중 **두 번째와 세 번째**에 해당한다. **첫 번째(다른 대안이
없어 불가피한 경우)에는 해당하지 않는다.**

이 점을 먼저 분명히 해둔다. 공식 명령 경로(`claude mcp list` + `claude mcp get`)는 **지금도
동작하고**, 그 경로가 만드는 컨테이너 누수도 같은 PR에서 회수 장치로 이미 덮었다. "공식
경로만으로는 기능이 성립하지 않는다"가 아니다.

해당하는 것은 아래 둘이다.

### 기준 3 — 가장 근본적으로 정확한 방법이다

이것이 이 예외의 핵심 근거다.

MCP 패널이 답해야 하는 질문은 "**지금 내 채팅이 실제로 쓸 수 있는 서버가 무엇인가**"이다. 그
질문에 답할 정보를 가진 주체는 **그 채팅이 붙어 있는 프로세스 자신**이다.

공식 경로는 그 프로세스에게 묻지 않는다. **별개의 CLI를 새로 띄워 서버들을 처음부터 찔러본
결과**를 대신 보여준다. 두 값은 어긋날 수 있다. 세션이 뜬 뒤 서버가 죽으면 세션은 그 서버를 못
쓰는데 패널은 `Connected`라고 쓰고, 세션이 붙잡고 있는 서버가 새 프로브에서 실패하면 패널만
`Failed`라고 쓴다.

즉 공식 경로는 **다른 질문에 답하고 있다.** 그 답을 아무리 잘 다듬어도 원래 질문의 답이 되지
않는다. 회수 장치로도, 파싱 개선으로도 해소되지 않는 종류의 문제다.

`mcp_status`는 그 프로세스 자신에게 묻는다. 어긋남이 구조적으로 존재하지 않는다.

### 기준 2 — 이득 차이가 압도적이다

정확성 하나만으로도 근거가 서지만, 나머지 차이도 한 방향을 가리킨다.

**사람이 읽으라고 만든 출력을 기계가 파싱하고 있었다.** `claude mcp list`/`mcp get`의 출력은
계약이 아니다. Windows 콘솔이 `✔`를 `√`로 치환한 것만으로 상태 판정이 깨진 적이
있다([#319](https://github.com/Swttch/swttch/issues/319)). `mcp-parser.ts`의
`stripStatusIcon()`이 그 사건의 산물이다. 게다가 `mcp-manager.ts`는 스스로 `claude mcp get`을
"brittle"이라고 적어두고 받아온 config를 버린 뒤 설정 파일에서 다시 읽어 덮어쓴다. **우리는
이미 그 출력을 신뢰하지 않고 있었다.**

**장치 세 개가 하나로 줄어든다.**

| 얻는 것 | 공식 경로에서 쓰던 장치 |
|---|---|
| 이름, 상태 | `claude mcp list` 텍스트 파싱 |
| scope | `claude mcp get` 텍스트 파싱 |
| config | 설정 파일 직접 읽기 (위 둘을 못 믿어서) |
| tools | 우리 MCP SDK로 서버에 직접 연결 |

`mcp_status` 응답 하나에 이것이 전부 들어 있고, 우리가 아예 못 얻던 `serverInfo`까지 온다.

"압도적"인지는 사람이 판단할 몫이고, 아래 「사용자 판단」에 적은 대로 개발자가 두 경로를 비교한
뒤 채택했다.

### 근거가 되지 못하는 것: 컨테이너 누수

`#363`의 발단은 새로고침당 컨테이너 2개였고 `mcp_status`는 그것을 0으로 만든다. 다만 **이것만
이라면 회수 장치로 충분했으므로 단독으로는 예외의 근거가 되지 못한다.** 위 두 기준에 더해지는
이득으로만 센다.

## 위반의 범위를 어떻게 좁혔는가

원칙 2번이 실제로 막으려는 것은 **종속**이다. "CLI에선 되는데 GUI만 막히는" 상태가 되는 것.
그래서 종속이 성립하지 않도록 세 가지를 강제했다.

- **공식 명령 경로가 코드에 살아 있다.** 문서상의 대체 방법이 아니라 지금 실행되는 코드다
  (`mcp-manager.ts`의 `listServersViaCli()`).
- **미문서화 경로가 실패하면 자동으로 공식 경로로 내려간다.** 응답이 없거나, 에러이거나,
  물어볼 CLI가 없으면(채팅 첫 메시지 전) 조용히 폴백한다. 사용자는 무엇이 실패했는지 알
  필요가 없다.
- **미문서화 경로가 영원히 사라져도 기능이 그대로 동작한다.** 느려지고 위에 적은 정확성·견고성
  문제가 돌아올 뿐, 없어지지는 않는다.

폴백 경로는 실제로 매일 실행된다. 채팅을 시작하기 전에 패널을 열면 그 경로가 답하므로, 죽은
코드가 되어 조용히 썩는 종류의 폴백이 아니다.

## 이 예외가 정당하지 않게 되는 조건

다음 중 하나라도 성립하면 이 예외는 철회하고 공식 경로로 되돌린다.

- 폴백 경로가 더 이상 실행되지 않게 되는 경우. 폴백이 죽은 코드가 되면 그 순간부터 이것은
  보조 최적화가 아니라 의존이다.
- `mcp_status`가 사라졌을 때 기능이 **없어지는** 경우. 느려지는 것은 허용, 없어지는 것은 불가.
- 공식 명령이 기준 2·3을 해소하는 형태로 개선되는 경우. 예를 들어 `claude mcp list --json`처럼
  기계가 읽는 계약이 생기고, 그것이 **실행 중 세션 자신의 상태**를 보고한다면, 기준 3의 근거가
  통째로 사라진다.
