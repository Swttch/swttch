# 아직 읽히지 않은 메시지의 「취소」에 미문서화 `control_request{subtype:"cancel_async_message"}`를 쓴다

> 마지막 갱신: 2026-11-16
> 수정 이력은 이 파일을 고쳐 적지 말고 `git log -- docs/principle-exceptions/697-cancel-async-message.md`로 확인한다.

- 관련 이슈·PR 번호: 아직 없다. 이 문서는 파일명의 번호 `697`을 PR 번호로 가정해 두었다. 실제 번호가 다르면 파일명과 아래 링크를 함께 바꾼다.

## 어떤 원칙을 위반하는가

`CLAUDE.md`의 **★ 핵심 원칙** 중 **2번 「공식 지원 비의존」**이다. "미문서화 내부 프로토콜에 의존하지 않는다."

**4번**이 허용하는 범위도 넘는다. 4번은 우리가 stdin으로 직접 제어하는 통신을 "보조 최적화로만 쓰며, 공식 CLI 명령 폴백을 항상 보장"하라고 한다. 이 요청에는 **폴백이 없다.** 이미 CLI에 쓴 메시지를 뺄 공식 방법이 없기 때문이다. CLI가 모르는 요청이면 취소 아이콘을 거두는 것으로 끝난다.

원칙 문장은 고치지 않았고, 여기 예외로 남긴다.

## 무엇이 문제였나

Claude가 일하는 동안 보낸 메시지는 우리 백엔드가 CLI의 stdin에 곧바로 쓴다. CLI는 그것을 받아 **자기 안의 대기열**에 넣고, 진행 중인 단계(예: 호출 하나)가 끝나는 지점에서 꺼내 모델에게 넘긴다. 쓴 뒤 6.2초 만에 읽힌 것을 개발 서버 로그에서 확인했다(`command_lifecycle`이 쓴 직후 `queued`, 읽힐 때 `started`).

Claude Desktop은 이렇게 아직 읽히지 않은 메시지를 말풍선으로 그리고, 그 아래에 취소하고 메시지 수정(X 아이콘)을 준다. 메시지를 CLI의 대기열에서 빼고, 글자·첨부·칩을 입력창에 그대로 돌려준다. 우리 플러그인에는 이것이 없어서, 사용자가 보낸 메시지를 거둘 방법이 없었다.

## 선택지

2026-11-16에 설치된 CLI 2.1.325로 개발 환경(개발 서버 + 내장 브라우저)에서 직접 재서 비교했다.

| 방법 | 취소 | 원칙 |
|---|---|---|
| 아무것도 하지 않음 | 불가 | 공식 |
| 공식 중단 `interrupt`(정지 버튼) | **메시지만 뺄 방법이 없다.** 턴 전체와 실행 중인 호출이 끊긴다 | 공식 |
| 보내기 전에 우리 쪽에 붙잡아 두기 | 쓰기 전이라 가능 | 공식. 그러나 "가능한 한 빨리 CLI에 쓰인다"는 스티어 모드의 약속이 깨진다. 한 번 이렇게 만들었다가 되돌렸다(개발자 지적) |
| `cancel_async_message{message_uuid}` | 그 메시지만 CLI의 대기열에서 뺀다 | **미문서화. 예외** |

## 이 요청이 어떤 것인가

CLI 실행 파일(`claude.exe`) 안의 요청 정의에서 읽었고, 실제로 보내서 응답을 받았다.

- **`{subtype:"cancel_async_message", message_uuid:<uuid>}`**: 대기열에서 메시지를 뺀다. 응답은 `{"cancelled": true|false}`이다. 이미 CLI가 읽었으면 `false`다. 실측: 메시지를 보내고 약 2초 뒤에 보내자 `{"cancelled":true}`가 왔고, 그 메시지는 이후 어느 응답에서도 읽히지 않았다.
- 요청은 메시지를 `message_uuid`로 지목한다. 그래서 stdin의 user 메시지에 `uuid` 필드를 넣어 쓴다(CLI 입력 메시지의 필드이고, CLI는 이 값으로 기록한다). 이 값은 요청 안에 문자열로 들어가므로 `^[0-9a-fA-F-]{8,64}$`만 받는다.

**같은 계열의 `interrupt{send_now:true, message_uuid}`는 쓰지 않는다.** "지금 보내기"에 쓸 수 있는 요청이지만, 스티어 모드의 메시지는 이미 CLI의 대기열에서 다음 입력 지점에 읽히므로 이 요청이 더하는 것은 진행 중인 단계를 비키게 하는 것뿐이다. CLI는 그때 실행 중인 것을 백그라운드로 옮기거나(`delivering`) 그 단계를 중단한다(`stopped`)고 정의하는데, Bash 호출로 시험하니 후자(`stopped`)가 나와서 호출이 "중지됨"이 되었다. 옛 구현(#220: 쓰기만 하고 CLI가 알아서 읽게 함)이 하던 자연스러운 끼워 넣기와 맞지 않아 넣지 않았다.

## 어느 기준으로 예외가 되는가

[README](./README.md)의 세 기준 중 **기준 1(다른 대안이 없어 불가피한 경우)**에 해당한다. 이미 CLI의 대기열에 있는 메시지를 빼는 공식 방법이 없다. 판단은 사람이 했다.

## 위반의 범위를 어떻게 좁혔는가

- **쓰는 것은 요청 한 모양뿐이다.** 응답의 `cancelled` 하나만 읽는다.
- **CLI가 `cancelled: true`로 답했을 때만 말풍선을 지우고 입력창을 되살린다.** `false`(이미 읽힘)이거나 에러이면 말풍선은 그대로다.
- **"CLI가 모르는 요청"**(`Unsupported control request subtype`, `not supported in this context`)이면 그 뒤로 취소 아이콘을 거둔다. 취소가 없어질 뿐 다른 기능은 그대로다.
- **차세대 트랜스크립트 보기(일반·생각·자세히)에서만 아이콘을 그린다.** 클래식 보기는 바꾸지 않았다.
- **다른 미문서화 요청과 따로다.** `set_model`, `apply_flag_settings` 같은 기존 예외와 무관하다.

## 이 예외가 정당하지 않게 되는 조건

다음 중 하나라도 성립하면 이 예외는 철회하고 공식 경로로 되돌린다.

- 이 요청이 사라졌을 때 **기본 메시지 보내기가 함께 깨지는** 경우. 취소만 없어져야 한다.
- 메시지를 지목해 CLI의 대기열에서 빼는 문서화된 공식 방법이 생기는 경우. 기준 1의 근거가 사라진다.
- `uuid`를 붙여 쓴 메시지가 CLI에서 다르게 기록되는 경우(대화 기록의 메시지 id가 우리가 정한 값과 어긋나는 등). 되감기·포크가 이 id를 쓰므로, 어긋남이 확인되면 `uuid`를 붙이는 범위를 줄인다.
